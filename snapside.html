Product History Platform

Snapside

プロダクトが作られるすべての瞬間を、
一つのHistoryにまとめる。

普段使うツールを一度接続すると、分散した変更を自動で収集し、Timelineから原文まで確認できるProduct History Platformです。

01 / Background

一つのプロダクトを、
複数のツールで作っている。

企画、デザイン、コード、データ、配信の記録は各サービスに残ります。しかし、プロダクト全体で何がいつ変わったかを確認するには、それぞれを開き直す必要があります。

02 / Problem

記録は存在する。
プロダクトの文脈が見えない。

新しい管理作業を追加せず、すでに各ツールで発生している変更からProduct Historyを構成する必要がありました。

01

変更が分散する

計画、画面、コード、配信の履歴が異なるサービスに保存される。

02

理由を探し直す

時間が経つと、何を変更したかだけでなく、その判断の背景も失われる。

03

手動記録が続かない

製品を作る作業とは別に、日報や作業ログを書く負担が生まれる。

04

結果だけが残る

完成画面だけでは、問題解決の過程と個人のContributionを説明しにくい。

05

AIも文脈を失う

AI Coding Toolが複数サービスの最新状態を一度に参照できない。

Design questionどうすれば新しい記録行動を求めずに、分散した変更を一つの製品史として残せるか。

03 / Competitive Landscape

プロジェクト管理ツールとは、
記録する対象が異なる。

公式ドキュメントを基に、各サービスの基本単位とユーザーが更新する情報を比較しました。3サービスは計画した仕事の進行を管理し、Snapsideは制作ツールで実際に発生した変更を収集します。

04 / Design Principles

収集は自動に。
確認はSourceに戻れる形に。

大量の変更を派手に見せるのではなく、個人が必要な時に経緯を読み直せる静かなインターフェースを基準にしました。

01Connect once

プロジェクトに一度接続すると、その後の変更を自動で収集する。

02Source-backed

各イベントから元ページ、File、Commit、Deploymentへ戻れる。

03Shared time axis

異なる形式の変更を、時間を共通軸として読み直す。

04Personal by default

チーム報告より、個人の判断・成長・Contributionを中心にする。

05Calm interface

多くのイベントを密度高く、優先順位を崩さず表示する。

05 / UX Decisions

変えたことと、
選択の理由を分ける。

3つの変更をコミットで確認。理由は設計仮説として示し、ユーザーへの効果とは区別します。

01

Issue作成を、一覧の中へ。

Before

一覧 → 別の作成ページ → タイトル＋作業内容

After

一覧＋作成欄 → 内容入力 → 担当者・優先度

コードから再構成したフロー図。実画面の比較ではありません。

問題仮説
一覧を確認しながらIssueを記録する場合、別ページへの移動と入力欄の分割が作業を中断させるのではないか、という仮説。ユーザー調査で確認した問題ではありません。
UXの判断
一覧内でそのまま記録できる構成にする。内容を一つの欄にまとめ、担当者と優先度は下部に配置する方針。
実装した変更
旧作成ページを一覧内のComposerへ接続。統合入力欄と担当者・優先度の選択を追加しました。
検証の限界 / 次のテスト
作成時間の短縮、作成率の増加は未検証。同じIssue作成課題で、所要時間・完了率・入力エラーを比較する。

06 / Core User Flow

一度接続し、
作業のたびにHistoryが更新される。

初期設定以降は記録のための操作を要求しません。Timelineで変更を探し、Event詳細から必要な原文へ戻ります。

  1. 01Create project

    製品単位のContextを作る。

  2. 02Connect sources

    普段使うServiceを選ぶ。

  3. 03Import history

    既存の変更を取り込む。

  4. 04Collect changes

    新しいActivityを自動収集。

  5. 05Review timeline

    週・日単位で流れを読む。

  6. 06Inspect event

    変更内容を読み、原文を開く。

  7. 07Use with AI

    MCPから最新Contextを読む。

No extra logging stepユーザーの主な操作は「接続」と「確認」。Historyを書くための入力画面をCore Flowに置かない。

11 / Outcome & Retrospective

結果だけでなく、
作ってきた過程を説明できる。

定量成果を作らず、現在実装した体験と、次に検証する課題を分けて整理しました。

ShippedUnified timeline

複数Serviceの変更を一つの時系列で確認する。

ShippedSource-backed history

各Eventから元の記録へ戻り、Contextを確認する。

ShippedEvent curation

EventにMemoを残し、不要な記録は非表示・復元できる。

ShippedMCP context

収集済みHistoryをAI Toolが読み、最新のProject Contextとして使う。

Evidence

実装の証拠と効果の証拠は異なる。

コード差分で確認できる変更を記載し、負担軽減や文脈維持は未検証の設計意図として扱います。

Next

同じ課題で変更前後を比較する。

Issue作成、特定機能の変更探索、初見Projectの状況説明を課題とする。ここではテスト実施や効果の確認は報告していません。
