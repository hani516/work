Problem framing

記録は増えるのに、知識は仕事へ戻ってこない。

企画はNotion、調査はChatGPT、思いつきはApple Notes、資料はDriveに残る。問題は情報の分散だけではなく、captureした記録と次のcreationの間で文脈が失われることでした。

Idea→Chat / Web→Notes / Notion→Forgotten→Search again
01 / Recall

場所ではなく、断片だけを覚えている。

正確なタイトルや保存先を思い出せず、検索の入口に立てません。

02 / Fragmentation

必要な根拠が複数のツールに散らばる。

ノート、AI会話、資料を行き来するほど、作業中の文脈が途切れます。

03 / Context loss

見つけても、次の作業へつながらない。

検索、コピー、前提説明を繰り返すたび、記録は未来の入力になれません。

Key UX decision

Prompt boxではなく、二つの操作でAIとの契約を作る。

@ は「AIが何を知るか」、/ は「AIが何をするか」を決めます。context selectionとtransformationを分けることで、Editorの主導権をユーザーに残しました。

A

Editor | Chat

常設Chatが視線と画面を占有し、AIとの対話が中心になる。

B

Prompt → Document

生成は速いが、ユーザーがAI出力のレビュー役になる。

Final

@ Context + / Action

AIの知識と行動を分け、Editorの中で必要な瞬間だけ接続する。

@ /

@ Reference

必要な記録だけを、今の文書につなげる。

Referenceは単なる添付ではなく、AIとのcontext contractです。自動取得だけに頼らず、ユーザーが根拠を明示的に選び、Editorの隣で原文まで確認できるようにしました。

  • 参照範囲をユーザーが決める
  • 原文へ戻れる導線を残す
  • AI結果を編集可能なブロックにする

Designing the AI logic

AI機能ではなく、context boundaryを設計する。

すべてのノートを毎回送るのではなく、ユーザーが選ぶcontextとシステムが探すcontextの役割を分けました。タスク別に候補を組み立て、数と文字量に上限を置くことで、信頼・速度・コストを同じUX問題として扱いました。

One product, two contexts

Mobileで集め、Desktopで考え、結果を次のcontextへ戻す。

DesktopとMobileを画面サイズの違いではなく、同じknowledge loopの異なる瞬間として設計しました。Capture → Synthesis → Artifact → Future contextがプラットフォームをまたいで循環します。

Desktop

Write · Compare · Reuse

長文Editor、複数Reference、反復的なAI Action。

Mobile

Text · Voice · Search

Quick capture、音声メモと文字起こし、自然言語検索。

From design to production

デザイン判断を、動くプロダクトまでつなぐ。

AI-assisted developmentを使い、問題定義、UX/UI、AI logic、実装、QA、配信後の改善を一つのループとして担当しました。広いproductivity suiteから始め、実装を通じて「contextを複利化するEditor」へproduct thesisを絞り込みました。
